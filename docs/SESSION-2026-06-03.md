## Order of operations

### 1. Diagnosed the ghost-ticket bug
Codex had pushed `4647188 fix(tickets): persist allocations by outcome code` and afterward reported "Guido has 0 tickets in Supabase". That was misleading. Actual state via `/api/admin/diag-tickets` (new endpoint I built in `428aa04`):

- Guido: **72 tickets** in DB
- 65 of them had **zero allocations** (ticket row existed but `ticket_allocations` was empty)
- Only 7 had real picks

Root cause: the old save flow was
1. POST → resolve outcomes
2. Match labels → if 0 matched, still passed validation because `matchedOutcomes.length === payload.allocations.length` was `0 === 0`
3. Upsert ticket
4. Delete existing allocations (nuked good ones!)
5. Insert empty `allocationRows = []` → no-op
6. Return `ok: true` 

That nuked legitimate picks when SyncRetry retried older drafts with empty allocations.

### 2. Fixed the ghost-ticket root cause (`7f446af`)
In `lib/product/supabase-provider.ts` `submitTicket()`, added explicit guards:
```ts
if (matchedOutcomes.length === 0) return { ok: false, reason: "La jugada está vacía." }
if (totalAllocated <= 0) return { ok: false, reason: "La jugada no tiene créditos asignados." }
```

`validateAllocations` from `lib/game.ts` already enforced sum === MATCH_CREDIT (10000), so the practical error message to users is "La jugada debe sumar 10000.".

### 3. Cleaned up the 66 orphan tickets (`7f446af`)
Built `app/api/admin/clean-empty-tickets/route.ts` that finds tickets with `allocations.length === 0` or `sum === 0` and deletes them via cascade. Ran once → deleted 65 Guido + 1 Jairo empty tickets.

### 4. Pushed recovery from localStorage (`4ff7e5c`)
Extended SyncRetry to re-push ALL `saved_remote` drafts (not just `sync_error`) on app load. **This was a mistake** — could overwrite newer data from another device. After SyncRetry ran from Guido's phone, his 65 deleted tickets came back from localStorage. He went from 7 → 72 tickets restored.

### 5. Reverted the dangerous SyncRetry (`c6bda5a`)
After confirming Guido's tickets were back, I reverted SyncRetry to only retry `sync_error` drafts. Reason: multi-device safety. If user picks A on phone (saved_remote in phone localStorage), then picks B on laptop (saved_remote in DB, but phone localStorage still has A), refreshing phone would re-push A and overwrite B. Bad.

### 6. Built recovery-from-events backup (`c6bda5a`)
`app/api/admin/recover-from-events/route.ts` rebuilds tickets from `pick_events` audit log if anything ever gets lost. Independent of any device's localStorage. **This is the recovery tool** if shit hits the fan in production.

### 7. End-to-end audit (no code change)
Ran via Chrome MCP: register fake user → save pick with `code` + `label` + 3 outcomes → save champion → try empty allocations (rejected) → try zero-sum (rejected) → logout → login → verify ticket still there. All passed. Confirmed system is bullet-proof for friend-tier usage.

CSS uses `position: fixed; left: 0; right: 0; display: flex; justify-content: center` with `max-width: calc(var(--shell-width) - 32px)` on the button itself.

## What to NOT touch / undo

1. **Do not re-add aggressive SyncRetry that retries `saved_remote`**. It causes cross-device overwrites. Only retry `sync_error`.
2. **Do not remove the empty-allocation guards in `submitTicket`**. They prevent the ghost-ticket bug from coming back.
3. **Keep the `pick_events` audit log fired AT THE END of submitTicket**, after allocations are confirmed inserted. Don't move it earlier.
4. **Do not commit `public/source-icon.jpg`** — was deleted intentionally.
5. **Do not change the `code` + `label` payload contract from frontend**. The 3 save components (deck, vote, detail) all send both. Backend prefers `code` and falls back to label.
